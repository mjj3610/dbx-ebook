## 2. 阻塞项：HTML 消毒覆盖不全

**根因**：注入点分散且有遗漏 —— `render.ts` 直接 `innerHTML`；`mobi.ts` 只用正则删 `script/style`；`markdown.ts` 放行任意 `href`；`utils.ts` 的 `sanitizeHtml` 漏 `xlink:href` / `formaction` / `srcdoc`。

**做法**：新增 `src/core/sanitize.ts`，所有格式的正文只在 `mountChapter` 落地，因此把消毒收口在这一个入口。

| 机制 | 规则 |
| --- | --- |
| 惰性解析 | 用 `<template>` 解析（脚本不执行、图片不发请求） |
| 危险标签 | `script/style/link/meta/base/iframe/object/embed/form/input/math/svg 的 foreignObject` 等**直接删除** |
| 无害容器 | `div/span/section/center/font…` 解包保留文字 |
| 属性白名单 | 标签级白名单（`a[href,name]`、`img[src,alt,width,height]`、`td[colspan,rowspan]`…） |
| 属性黑名单 | 所有 `on*`、`style`、`srcdoc`、`formaction`、`http-equiv`、`nonce`、`integrity` |
| URL 协议 | 先剥离 `U+0000–U+0020`、`U+007F–U+009F` 再判协议，只放 `http/https/blob`；`data:` 仅限 `img` + `data:image/*` |
| SVG | 只保留 `svg/g/image/path/rect/circle/…`，`xlink:href` 按 URL 规则校验 |

回归样本：`fixtures/evil-html.html`（1,430 B）与 `fixtures/evil-md.md`（252 B），payload 全部写入 `window.__pwned`。e2e 的 `[4d]` 10 项断言覆盖 `java&#115;cript:`、`jav\tascript:`、`xlink:href`、`srcdoc`、`formaction`、SVG `foreignObject`、`<meta http-equiv=refresh>`，并确认正文没有被误删。

## 3. 用户反馈：PDF 仍有部分乱码

分两层，是**两个不同的原因**：

### 3.1 页面正文（v1.2.3 已修，本版加固）

判据：字体坏是「按字体」坏的，而封面与内页用的是不同字体子集。原来只体检第 1 页，遇到「封面正常、内页全花」的文件会漏判。

- 采样页从「仅第 1 页」改为「前 2 页 + 中段 + 末页」，任一页可疑率 ≥10% 即切兼容模式（提前返回，不会把 161 页全走一遍）
- 同时统计 `showSpacedText`（原实现只看 `showText`），并把「拿不到 Unicode 的字形」也计入可疑

实测（161 页 / 58 MB 周报）：兼容模式下 **161 页、0 个 `fontChar ≠ unicode`**，即正文不会再出现错字。

### 3.2 文档元信息（本版新修）

`pdf.js` 按 PDFDocEncoding 解 Info 字典，而 PowerPoint 写入的是 UTF-8 字节，于是出现：

```
Title  : Microsoft PowerPoint - SQCSå‚¨æ−¥æ±⁄æ•»-WK01
Author : Qiuyu Chen(éŽ‹ç§‰ç¾½)
```

`0x91` 会被 PDFDocEncoding 显示成 `‚`、`0x8A` 显示成 `−`，所以不能简单按 Latin-1 还原。新增 `repairMojibake`：

1. 用 `PDFDOC_SPECIAL_BYTES` 表把 0x80–0xA0 的特殊标点换回原始字节
2. 用 `TextDecoder('utf-8', { fatal: true })` 严格解码
3. 只有解出汉字/韩文，或不再含 Latin-1 补充字符时才采用，否则原样返回（正常西文不动）

结果：`SQCS周报汇总-WK01`、`Qiuyu Chen(陈秋羽)`；`Café résumé`、`Microsoft: Print To PDF` 保持原样。PDF 大纲标题同样走这一步。

## 4. 用户反馈：路径选择改用资源管理器

**先确认限制**：宿主下发的 CSP 是 `connect-src 'none'`，页面处在 `sandbox="allow-scripts"`（origin 为 `null`）的 iframe 里，Chrome 明确拒绝沙箱页面打开系统选择框（`Sandboxed documents aren't allowed to show a file picker`）。逐一排查后确认宿主也**没有**暴露目录选择 API：二进制里只有 `host.clipboard / host.data / host.network / host.storage / host.events / host.requestUserInput` 等，`showDirectoryPicker / pickFolder / openFileDialog` 均为 0 命中。所以「系统对话框」这条路在当前宿主里走不通。

**改成两条真实可用的通路**：

1. **`storage/reveal`（新增后端方法）**：用 `explorer` / `open` / `xdg-open` 在当前目录拉起系统资源管理器，用户在里面随便浏览，复制地址栏路径回来即可
2. **可编辑地址栏**：地址栏点击即变成输入框，`D:\Books` 粘进去回车直接跳转，非法路径回一条提示且不破坏当前目录

**顺带修掉「文件夹显示不全」的真因**：`.ellipsis` 只有 `min-width:0`，在 380–520px 的窄面板里会被挤到只剩首字；侧栏固定 176px 又吃掉一半宽度。

- `.ellipsis` 改为 `flex: 1 1 auto`
- `≤620px` 时改为上下布局：磁盘/快捷位置变成顶部标签行，列表占满整行

实测（`probe-picker`）：视口 520px → 侧栏 365px、条目宽 318px，前 12 个目录名**全部完整**（3D Objects / IntelGraphicsProfiles / jxbrowser_tmp 等长名不再截断）；900px → 侧栏 160px、条目宽 463px。

## 5. 隐藏缺陷：宿主里 `fetch` 全部失败（本版一并修）

**这是评审「host.network 只有 3 个 origin」背后的真问题**：不是白名单太窄，而是**页面根本发不出任何请求**。

实测（dev 宿主，与正式宿主同一套 CSP）：

```
页面内 fetch('https://api.openai.com/v1/models') → throw Failed to fetch
host.request('host.network', …)                  → Unsupported mock host method: host.network
```

也就是说 v1.2.4 及之前，**翻译与 WebDAV 备份在真实宿主里 100% 不可用**，只有 `npm run dev` 的普通浏览器里能跑。

**做法**：出网整体下移到原生 Sidecar。

- 新增 `net/request`：后端用 `http.Client` 直接联网，只放行 `http`/`https`（`file://` 被拒），响应体上限 16 MB，超时可配
- `net/request` 不参与全局锁 —— 一次翻译可能几十秒，占着锁会把 `book/read`、`library/write` 全卡住
- 新增 `src/core/net.ts`：`netFetch()` 在宿主里走 `net/request`，纯浏览器里退回原生 `fetch`，调用方拿到的是标准 `Response`，`translate.ts` / `webdav.ts` 只换了一行
- `manifest.permissions` 从 3 条 `host.network:*` 改为**空数组**：页面不再发起任何网络请求，域名由用户填写，本来就无法预先枚举

实测（`scripts/host-net.mjs`，4/4 通过）：

```
[1] 页面内 fetch 被沙箱拦截（符合预期）  fetch → throw Failed to fetch
[2] 后端能连外网并取回响应体            net/request → {"status":200,"bytes":772}
[3] file:// 被拒绝                      只支持 http/https 地址
[4] 资源管理器打开成功                  reveal → {"ok":true,"path":"…\\dbx-ebook\\library"}
```

副产品：PR 里「任意 OpenAI 兼容接口」「Nextcloud / 群晖」的说法**现在才真正成立**。

## 10. 已知限制

- **PDF 兼容模式会换字体**：字形来自系统字体，与原文排版略有差异（界面已有提示条说明）；这是「字对」和「形似」之间的取舍
- **PDF 元信息还原只覆盖 UTF-8 误解码**：GBK 字节被当 Latin-1 解出来的 `Âí¼Ì¾¼` 无法还原，此时按原策略丢弃该字段（标题退回文件名）
- **`net/request` 是本地转发**：不做域名白名单，用户在设置里填什么就访问什么；只限制协议与响应体大小。若后续宿主提供 `host.network` 代理，应改回宿主代理以获得统一审计
- **目录选择仍不是系统对话框**：宿主未暴露该能力前无法做到；当前提供「地址栏输入 + 资源管理器按钮」两条替代通路
- **包体积 7.1 MB**：主要来自含 TLS 的后端
